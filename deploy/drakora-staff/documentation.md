# Staff portal and Discord Office

## Identity and access

The Express service provides Discord OAuth, an OpenID Connect issuer for Huly, and a reverse proxy that checks every Huly HTTP request and WebSocket upgrade. The React dashboard and Office use same-origin authenticated APIs.

The Dashboard role is required for Discord sign-in and all staff sessions. The Todo role is additionally required for Huly and Office access, alongside their saved dashboard permissions. Without Todo, Huly is absent from the dashboard. Rank roles never grant either access permission. Founder maps to Huly Owner, Manager and Admin to Maintainer, and the remaining configured ranks to User. Specialist ranks can appear only in Huly. A member with several ranks receives the highest configured permission level and all corresponding project role labels.

The Huly Contacts Role column also shows all configured Discord ranks for employees linked to a staff account. The staff gateway resolves those rank names from the connected Discord bot roster and the stored Discord to Huly account link. The browser refreshes the badges every fifteen seconds while Contacts is open. Huly's generic HR Worker badge is hidden only in this staff deployment; the HR mixin remains on the contact. A disconnected bot clears rank badges instead of showing stale assignments. Employee and GitHub badges remain unchanged.

The first dashboard or Huly visit after Discord login requires a Minecraft Java Edition username. Existing staff see a welcome-back prompt. The name is stored under the stable Discord ID in the encrypted database, is case-insensitively unique among current links and pending change requests, and is marked `pending` for later in-game verification. Staff may continue immediately while it is pending. A member cannot directly overwrite a submitted name. They can request a change in Settings; the `accounts.minecraft` permission is required to approve or reject it, granted to Founder and Manager by default. An approved name remains pending verification. By default, Founder, Manager, and Admin can view registered accounts, linked names, pending requests, current configured Discord staff ranks, and last observed Discord activity in Accounts. Ranks are unavailable while the Discord Office connection is down. This view does not expose OAuth tokens or Huly account secrets. Minecraft server last-login activity and ownership verification are deferred until the server integration is available.

The dashboard Settings page requires the same Dashboard role as Overview. Its accent preference accepts 3 or 6 digit hex colors, normalizes them to 6 digits, and stores them under the Discord account ID in that browser's local storage. It changes dashboard controls and accents only; the sign-in screen, Huly, and Office keep their own appearance. Reset removes the saved preference. No preference is sent to the server or synchronized between browsers. Minecraft name links and change requests are stored on the server instead.

Discord IDs are the persistent identity. The verified Discord email allows Huly to link an existing account during OpenID sign-in. A valid, email-bound workspace invitation also permits Huly account creation when public signup is disabled. The original recovery owner remains an owner internally, while the public proxy still requires both Dashboard and Todo roles. Preserve private recovery access separately.

Sessions last twelve hours and use Secure, HttpOnly, host-only cookies. A Huly session depends on its originating staff session. Signing out closes related live connections. A single-use, browser-bound handoff connects the two host sessions. Background requests receive an authentication error instead of restarting the login flow. Role checks refresh after sixty seconds, and open WebSockets are rechecked every thirty seconds. Losing Dashboard blocks an existing session at its next role check. Meeting mutations force a fresh role check and require an origin match and session CSRF token.

The staff proxy adds `STAFF_SSO_URL` to Huly's browser configuration and hides Huly's local login and signup controls. A Huly login page reached without a valid app session returns to the existing staff session and runs the OpenID handoff. A 30 second browser guard prevents repeated redirects if the handoff fails; the OpenID provider button remains available to retry. The gateway still checks Dashboard and Todo roles before exposing Huly.

The proxy also sets `STAFF_DASHBOARD_URL` to the staff portal origin. In this deployment, clicking the top-left Huly logo returns to the staff dashboard. The profile menu still offers Select Workspace. Without that configuration, the logo retains Huly's normal workspace menu.

Discord profiles sync during authenticated activity. Guild avatars take precedence over global avatars, with Discord's default picture as a fallback. Huly stores an external avatar URL and loads it from Discord's CDN. A changed picture updates after the next role refresh; a browser refresh may be needed to replace an already-rendered Huly profile.

## Discord channels

Create one private Staff Office category containing:

| Channel         | Type           | Default state           |
| --------------- | -------------- | ----------------------- |
| All Hands       | Voice, meeting | Locked                  |
| Meeting Room 1  | Voice, meeting | Locked                  |
| Meeting Room 2  | Voice, meeting | Locked                  |
| Voice Room 1    | Voice          | Open                    |
| Voice Room 2    | Voice          | Open                    |
| meeting-invites | Text           | Visible to Todo members |

Deny View Channel and Connect to everyone. Allow View Channel, Connect, and Speak to the Todo role on the category and casual voice rooms. Meeting rooms override the Todo role's Connect permission to deny until started. Discord administrators retain their platform-level permission bypass. Avoid other role or member overrides that independently grant access to meeting rooms.

The bot needs View Channel, Manage Channels, Manage Roles for channel permission overwrites, Connect, Speak, Send Messages, Embed Links, Read Message History, and permission to mention the Todo role. Limit its permissions to this category where practical. The bot must be able to edit the configured role's overwrites. The service validates channel types and category membership before mutations.

The Office uses Guilds, Guild Members, Guild Presences, Guild Voice States, and Guild Messages Gateway intents. The two privileged intents must be enabled in Discord's Developer Portal. Message Content Intent is unnecessary. The browser refreshes its view every five seconds. Invisible members appear offline. The roster includes all non-bot staff server members for authorized Todo users, with active staff highlighted separately. Voice state remains in memory.

Last active combines observed online presence and message creation timestamps from the staff guild and optional `activityGuildIds`, with at most two distinct guilds in total. Only current staff guild members contribute records. Direct messages, bots, webhooks, system messages, and other guilds are excluded. Message bodies are not inspected or retained, and the gateway disables its message cache. Timestamps are kept in the encrypted staff database for ninety days. A message updates the exact timestamp even within the presence write interval; older events cannot rewind newer activity.

After connection and resume, a background refresh reads the latest 100 messages per readable channel and active thread in the configured guilds. It requires View Channel and Read Message History. Inaccessible channels are skipped without blocking Office. This bounded refresh is not a complete Discord history import and does not scan archived threads. Only the latest activity timestamp survives the scan. Live message events continue updating activity without relying on visible presence. Shutdown waits for the refresh before closing the database.

Huly's Office keeps its original floor and room layout. Clicking a room tile opens Huly's native room view. The Discord control in the Huly header opens staff presence, the searchable server roster, room occupancy, voice links, and Discord meeting actions. Discord room status remains visible on matching tiles. Huly's native audio and video connection requires a separately configured Love service and LiveKit endpoint; opening a room does not start or unlock a Discord meeting. The dashboard no longer includes a separate Office navigation item. Minecraft game activity is reserved for the later proxy unification.

The Drakora Huly frontend excludes the current Chat application, the legacy Chunter application, and HR from workspace navigation. Their models and existing records stay intact, including previously created meeting minutes. This is a navigation change, not a data migration.

## Meeting lifecycle

Only configured meeting host roles with Todo access can start or end a meeting. A start first persists an operation record, unlocks the room, then sends one private invitation mentioning only the Todo role. The invitation's button opens the voice channel in Discord. The UI asks the host to confirm before sending.

Operations on each room are serialized. Repeated starts while live return the existing meeting and do not send another invitation. Failed invitations trigger an attempt to relock the room. An unsuccessful close remains recoverable and blocks another start. Ending a meeting locks new joins and edits the existing invitation without another notification. It never disconnects voice participants.

Meeting state is persisted in the encrypted database. After restart, live meetings remain open; incomplete operations are reconciled to closed. Initialization retries are bounded. If Discord cannot be reached or permissions no longer match, the UI shows unavailable controls. Restart the service after correcting persistent configuration or permission errors.

An ambiguous Discord send timeout can leave an invitation whose delivery was not acknowledged. The room is relocked when possible; inspect the invitation channel after such an error. Do not infer that a message was never delivered from a failed HTTP response.

## Configuration and services

`server/discord.js` owns OAuth token refresh and access checks. `server/huly.js`, `profile.js`, and `project-roles.js` reconcile Huly workspace membership, pictures, and the default tracker project's named roles. `office.js` owns the Gateway connection and Discord operations; `meetings.js` owns durable meeting transitions. `store.js` encrypts records with AES-256-GCM in SQLite.

The Huly account endpoint defaults in the example to `http://account:3000`; the upstream proxy points to `http://nginx:80`. Profile and project reconciliation use `http://transactor:3333` on the shared private Docker network. The tracker project ID is `tracker:project:DefaultProject`.

Keep the public domains exclusively behind the staff proxy. An independently public Huly origin would bypass the Discord role gate. The proxy expects a trusted TLS terminator and is bound to loopback on the host. If using Cloudflare Tunnel, point both hostnames at `http://staff:3000` on the shared network and retain normal TLS protection. Keep tunnel credentials outside the checkout.

The optional Office configuration includes the category, invitation channel, allowed host role IDs, and an ordered list of meeting or casual voice rooms. Removing it disables the integration server. Build the matching Huly frontend before exposing the Office configuration to clients.

## Discord staff rank synchronization

With Office enabled, `roleSync.guildId` identifies the main Drakora guild and `roleSync.roles` contains explicit `{ "staffId": "...", "mainId": "..." }` pairs. The staff guild remains `guildId`. Each role can appear in only one pair. Staff IDs must be configured ranks or application specialist roles; Dashboard and Todo access roles cannot be mapped. The current configuration maps Founder, Manager, Admin, Sr Moderator, Moderator, Jr Moderator, and Helper. Specialist roles are independent unless separately mapped to matching roles that exist in both guilds. Remove the optional `roleSync` block to disable synchronization.

The existing Office bot connection receives member additions and role updates in both guilds using the Guild Members intent. Give the bot Manage Roles and place its highest role above every mapped rank it must add or remove. Being above Manager permits Helper through Manager; Founder changes wait until the bot is above Founder as well. The service validates each mapping against actual guild roles and never creates roles or replaces an entire member role list. Unmapped roles and the independent Dashboard and Todo access gates remain unchanged. Staff-guild member updates invalidate cached portal role checks so the next protected request refreshes permissions; the normal role-based application and Huly rules still apply.

Set `roleSync.initialSource` to `staff` to resolve initial conflicts using the staff guild. A sole existing assignment is copied to the other guild, including when the other member already exists without a mapped rank. `main` selects the main guild instead; `unchanged` leaves conflicting initial ranks unresolved until a new rank change supplies an intent. After initialization, a real role change in either guild replaces the desired mapped role set, including an empty set for a removal. The last observed change wins. Reconnects inspect current membership: a change made while disconnected in one guild takes precedence, while conflicting changes in both use the configured initial policy. Discord does not provide missed edit timestamps, so their true chronological order cannot be recovered.

`server/role-sync.js` stores desired roles, observations, delivery state, and bounded expected bot updates as encrypted `discord-role-sync` records in the staff SQLite database. These records do not expire. Missing members and incomplete membership screening keep pending assignments through restarts. Joining the destination guild applies the saved assignment; leaving and rejoining does not erase it. A newer promotion, demotion, or removal replaces an older pending assignment. Per-member workers serialize changes and ignore expected bot updates, including intermediate removal and addition events, so a copied event cannot overwrite a newer intent or loop between guilds.

Permission, hierarchy, and temporary API failures retain the desired assignment and retry at most once per minute during normal operation. Role configuration events prompt an immediate retry. A blocked member does not stop other members from synchronizing. Missing members wait for a join event or reconnect instead of being polled each minute. The sync uses only individual role add and remove endpoints and does not send Discord messages. Back up the staff database and its encryption key to preserve pending assignments.

## Discord to-do forums and Tracker

Create a Huly Tracker project for each Discord forum to-do list. Set `todoForums` in the private staff configuration to distinct `{ "channelId": "...", "projectId": "..." }` pairs. The bot must be able to view the forum and its posts. Add a URL property named `Discord post` to Huly's Issue type; the service uses that property and a stable Discord thread ID to prevent duplicate imports. It imports current and public archived forum posts and polls every five minutes. A changed Discord title or workflow tag updates the corresponding Tracker issue. Other Huly edits remain intact until that source value changes. There is no reverse sync, and comments, attachments, assignees, and non-workflow forum tags are not copied.

The forum tag `In Progress` maps to Huly In Progress, `Complete` to Completed, and `Vetoed/Not Possible` to Impossible / Void. `Awaiting Verification` maps to the same-named status when present. A post without a workflow tag starts Pending. Use Huly statuses for progress and Huly labels for pack, server, and issue classification. The current labels cover Prom2, Luna, Terra, Sol, RestLess Horizons (RH), Eclipse, Void, EU Proxy, NA Proxy, Hub, Bug, Glitch, Exploit, and PRIORITY. Huly's own issue changes do not change Discord forum tags.

## Backups and recovery

Back up the private configuration, SQLite database, and `oidc-jwks.json` together using a consistent SQLite backup or a stopped service. The database key is required to recover encrypted records. Keep backups encrypted or access-restricted and outside Git. Back up Huly's databases and object storage using its deployment procedures as well; a source fork is not a data backup.

Retain the previous staff and Huly front image identifiers before deployment. To roll back, restore those images and their matching source and configuration. Restoring an older meeting database can disagree with current Discord permissions, so inspect and reconcile managed rooms before reopening Office access.

## Verification

`pnpm test` checks independent access roles, rank ordering, encrypted persistence, one-use handoffs, role revocation, background login behavior, meeting serialization and recovery, avatar URL selection, and forum issue import and reconciliation.

For a live installation, verify a user with each access combination, the Huly Office iframe, avatar rendering, and a real voice join. A host should start and end a test meeting with participants aware that the Todo role will be notified. Confirm the invitation opens the correct channel, regular Todo members cannot join before start or after end, and existing participants remain connected after end. Browser-only checks do not establish audio connectivity.

## Application storage and delivery

Applicant DMs use teal receipt, blue review, green approval, and red denial accents, with written status labels and welcoming messages addressed to the applicant's preferred name. Their linked Discord avatar appears as a thumbnail when available. Approval messages explain that the team will help with the next steps. Denials thank the applicant and show both the full date and time remaining before reapplying for that role. Applicant-facing staff feedback is kept in a separate matching color embed so the complete message fits Discord's limits. The footer retains the application reference. These presentation changes apply to newly queued messages; previously delivered messages are not rewritten.

Application sign-out removes the draft's linked Discord identity and confirmation and persists a marker requiring fresh Discord authorization on reconnection. The application OAuth challenge carries that preference, so an existing staff session cannot silently reconnect the account just disconnected. The marker clears after a successful new connection. Draft answers, staff sessions, and Huly sessions are preserved.

When configured, applications use a separate encrypted SQLite store mounted at `/applications`. Records include the submitted answers, questionnaire version, assigned scenario, contact email, optional Discord identity snapshot, and an unverified Minecraft name and resolved profile UUID. Roles used to determine available application types are read from Discord identity responses, never accepted from the form. No Discord bio or applicant OAuth access token is retained. Future network activity fields remain empty until a server integration supplies evidence.

Registered staff who connect Discord receive their Minecraft name from the panel registry under their verified Discord ID. The form requires confirmation of that exact name. Selecting an incorrect name directs them to panel Settings for a change request. A pending change blocks submission until Founder or Manager approval or rejection. An approved name change invalidates the previous confirmation. The server rejects attempts to substitute another name and rechecks the linked name after profile lookup before committing the application. Ordinary applicants without an active staff rank and registered link still enter their name manually.

Public mutations require the public origin and a session-bound CSRF token. Public sessions use a separate host-only Secure, HttpOnly, SameSite Lax cookie. Discord identity handoffs expire, are consumed once, and are bound to the browser session that started the application. Using the optional public sign-in never grants dashboard access or replaces an existing staff session. Form bodies and request rates are bounded. Only the application route and its assets are exposed on the public host.

Evidence is optional. `answers.experienceLinks` holds up to five newline-separated HTTP or HTTPS links, without embedded credentials. Links are validated before submission and are never fetched by the service. Required-question metadata is shared between server validation and the form's red asterisks, with screen-reader labels identifying required fields.

Portfolio and evidence questions provide an Imgur upload shortcut in a separate tab. Applicants host screenshots there and paste image or album links into the application. The service stores the submitted text and URLs only; it never fetches linked images, accepts image uploads, or stores image bytes in the database. The former public and staff image endpoints are unavailable. Evidence links appear on the applicant's final review and the private staff application detail. Discord notifications do not include evidence links.

Applicants who answer that they do not use Discord receive a final required Yes/No question about downloading Discord for staff communication if approved. Both answers allow submission and appear in the private staff view. Connected Discord users and applicants who already use Discord skip this question. Earlier questionnaire versions display that the question was not asked, rather than inferring an answer.

Submission writes the application, list summary, staff notification, applicant confirmation for the selected notification method, and receipt atomically. Repeating submission from the same draft returns its existing reference without scheduling duplicate messages. `server/application-notifications.js` owns the durable encrypted outbox. It retains compatibility with existing staff notification jobs. Temporary delivery failures retry with backoff up to eight attempts; Discord's reported rate limit delays are respected. Other HTTP client errors stop that message without retrying. A failed delivery does not lose the application. Every notification disables user, role, and automatic mentions, even when the display text includes a Discord user mention. Discord's deterministic nonce reduces duplicate messages within Discord's recent-message uniqueness window; it does not guarantee indefinite exactly-once delivery after an uncertain network result.

Only the verified Discord account linked at submission can receive applicant Discord updates. The encrypted worker outbox sends immutable event messages for Received, Reviewing, Approved, and Denied in order. Messages include the role, reference, and applicant-facing decision message, but never private staff feedback or questionnaire answers. Temporary failures and rate limits retry; blocked DMs (Discord 403/50007) use the configured private fallback. Other errors do not create channels.

Configure `applications.fallback` with `guildId`, `categoryId`, and `reviewerRoleIds`, using IDs from the main guild. The bot requires Manage Channels and permission to view, send, embed, and read history. Use the main guild's moderation roles equivalent to Jr Moderator and above. Every fallback checks current membership, role existence, category ownership, and channel ownership. Creation includes private overwrites atomically: deny View Channel for everyone, grant view/reply/history to the applicant and reviewers, and embedding to the bot. Before every post, unexpected overwrites are repaired and checked; a failed repair prevents delivery. Discord administrators inherently bypass channel restrictions. The worker reuses its stored channel or recovers a channel by its exact ownership topic after an uncertain creation response. Channels are retained until operator removal.

`notificationPreference` is a protected identity field, not an editable questionnaire question. Linked applicants default to Discord; anonymous applicants use email. Explicit email selection requires `contactEmail` even if Discord supplies a verified address. Email opt-out suppresses applicant Discord updates and channel creation, while staff channel notices continue.

Email events enter the encrypted `application-email-notification` outbox with recipient, event, payload, queue time, attempts, and next delivery time. With `applications.smtp` configured, the notification worker sends these through a private Unix socket to Proton Bridge using Nodemailer, mandatory STARTTLS, and the configured trusted certificate. Bridge remains bound to loopback; a user systemd socket and `systemd-socket-proxyd` relay provide container access without a network listener. The relay directory and socket use modes 0700 and 0600. Credentials and the certificate remain in private deployment configuration. See [the setup instructions](README.md#proton-bridge-email-delivery).

Submission, review, and decision emails use plain text and escaped HTML with status colors and clear next steps. They include only preferred name, application type, applicant-facing decision feedback, reapplication deadline, and reference. Questionnaire answers, internal staff feedback, email addresses of reviewers, attachments, and tracking pixels are excluded. The link opens the public application page; receipt access still requires the submitting browser. Optional `replyTo` directs replies to support. The optional shared mailbox described below lets authorized staff read and answer those replies.

Email updates are processed in chronological event order with at most twenty jobs inspected per worker pass. Temporary failures retry with exponential delays, up to eight attempts. Permanent recipient rejection records failure without deleting the application. Authentication errors retry rather than immediately discarding queued messages. No raw SMTP response, credential, or message content is logged. Each event has a stable Message-ID; delivery is at least once because an SMTP acceptance followed by a process crash before persistence can cause a retry. The existing `application-dm-delivery` records also store email delivery with `route: email`. API delivery states distinguish awaiting setup, queued, accepted by the email service, and failed. SMTP acceptance cannot prove inbox arrival or detect later bounces. Without SMTP, existing outbox entries remain waiting. Enabling SMTP resumes queued email events. No previously delivered Discord update is replayed as email.

The receipt is accessible only through the submitting browser session, expires with its seven-day draft, and exposes name, role, review status, notification preference, contact email, and delivery states. `PUT /apply/api/notifications` requires that session, matching Origin, and CSRF token; it accepts only preference and email. Preference changes finish in-flight delivery, then transfer unsent updates to the selected outbox. Changing contact email after denial also preserves the same-role cooldown for the new address. Delivered Discord messages are not removed. Existing applications default to their previous contact method; no earlier confirmation or failure is automatically replayed.

`GET /apply/api/history` returns current and previous applications in pages of twenty, newest first. The server matches Discord submissions to the currently connected, verified account. Submissions without Discord match a hash of the submitting browser session; an older current receipt also provides ownership evidence, which is retained when starting another application. Email addresses, Minecraft names, and request parameters cannot establish ownership. The response contains only application references, role labels, Minecraft names, submission dates, and current review statuses. Signing out or switching accounts removes access to the previous Discord account's history. Refresh updates reloads both the receipt and history; private answers and staff feedback are never included.

The configured staff notification channel also receives review, acceptance, and denial updates. Each names the acting Manager or Founder and applicant with silent Discord mentions when available and links to the private application. Review notices are blue, acceptance notices green, and denial notices red. Denials include the applicant-facing reason, minimum waiting period, and both the date and relative time when that application type becomes available again. Private feedback and questionnaire answers are not posted. Event snapshots preserve the original reviewer, decision, and reason if delivery occurs after another status change. Repeating an existing review does not enqueue duplicate channel notices, and existing statuses are not backfilled.

Within each delivery batch, applicant DMs are attempted before channel updates. A channel post reports whether that event's DM has been delivered, has failed, or is still queued at posting time. Applicants without linked Discord accounts receive no DMs, and channel notices direct staff to their contact details. Retry delays or a backlog may leave a DM queued when its channel notice is posted; the existing notice is not rewritten after a later DM delivery.

The staff list is paginated. Every list and detail request rechecks the authenticated Discord permissions and requires the Dashboard role and `applications.view`, granted to Jr Moderator and higher by default. Staff sessions retain the existing one-minute role refresh interval. Viewing an application does not change its status. Notices link to `/applications/{id}`, and sign-in preserves that destination.

`GET /api/applications/{id}/history` uses the same staff permission check and returns other stored submissions by that applicant in pages of five, newest first. The current application is excluded. When both applications are linked to Discord, their account IDs must match; different Discord accounts never match through shared contact details. When either application has no Discord account, both normalized contact email and Minecraft name must match. Anonymous matches do not establish ownership or change applicant receipt access. Existing submissions require no migration. Responses contain only references, role keys, Minecraft names, submission dates, and current statuses, with `Cache-Control: no-store`. The review side panel displays those summaries with colored status badges, direct review links, pagination, and loading, empty, and retry states. Opening a previous application preserves the staff list filters.

Application details use a wider review layout with applicant answers and feedback on the left and a player information panel on the right. Approval controls are green, denial controls red, and review controls blue; status badges also retain their written labels. The player panel shows the submitted Minecraft name and profile identity, with a Minecraft skin avatar at the top right. The avatar uses [MCHeads](https://mc-heads.net/) through the existing image proxy on the staff host, preferring the resolved UUID over the name. Images are streamed without application database storage. An unavailable preview is hidden while the name and verification status remain visible. Network playtime, first join, recent activity, playtime per server, proxy sessions, tickets, reports, and moderation history are explicitly marked as not connected until their integrations provide data. Missing statistics are never displayed as zero or treated as a clean moderation record. The layout stacks on smaller screens.

The `applications.comment` permission allows private feedback, granted to Jr Moderator and higher by default. Feedback has a server-authenticated author and timestamp and is limited to 100 entries per application, with 3 to 4,000 characters each. The separate `applications.review`, `applications.approve` and `applications.deny` permissions control review and decisions, granted to Managers and Founders by default. `POST /api/applications/{id}/review` changes Received to Reviewing and records the initiating reviewer and time. Repeating it while Reviewing preserves the original review and does not enqueue another notification. Viewing an application does not start review. `POST /api/applications/{id}/decision` accepts `decision`, `reason`, and, for denial, `reapplyDays`. Received and Reviewing can become Approved or Denied; final decisions cannot be overwritten. Reasons are optional and limited to 2,000 characters. An omitted, empty, or whitespace-only denial reason is replaced by a generic applicant-facing message, saved with the decision and included in applicant and staff notifications. Approval does not receive a generic denial message. Status, summary, cooldown, applicant DM, and staff channel notification update in one transaction. Feedback, review, and decision mutations force a fresh Discord role check, match the staff origin, and require the session CSRF token. Decisions do not grant Discord roles.

A denial accepts a whole-day wait from 0 to 365, defaulting to seven days when omitted. Zero adds no new cooldown and permits immediate reapplication unless an earlier same-role wait still applies. The deadline is calculated from server time and stored as `decision.reapplyAfter`; a later denial cannot shorten an existing wait. Existing denials retain their original deadlines. Cooldowns apply only to the denied role and expire at their deadline. The server checks them both before profile lookup and inside the final submission transaction, so a concurrent denial also blocks a new submission. A new browser draft or service restart does not reset the deadline. Known cooldowns appear in the public role selection. Cooldown keys match the verified Discord ID and the normalized contact email plus Minecraft name pair. Because Discord is optional and anonymous email and Minecraft ownership are not verified, anonymous matching cannot prevent someone from claiming entirely different identity details. There is no automatic cooldown backfill for earlier denials.

Back up `applications.sqlite` with a consistent SQLite backup or while the service is stopped. Retain the independent encryption key separately in protected configuration; losing it makes existing records unreadable. Copying a live SQLite main file without its WAL can omit recent records. Draft and temporary handoff records expire automatically, but application records are retained. Account deletion, retention policy changes, automatic Discord role assignment, and Minecraft verification require separate product changes.

## Application filters and question editing

`GET /api/applications` accepts `offset`, `role`, `status`, and `name`. Supported roles are `community`, `builder`, `artist`, and `developer`. Stored status values are `Received`, `Reviewing`, `Approved`, and `Denied`; the UI labels Reviewing as In review. The optional `name` string is limited to 80 characters and matches literal substrings in preferred names, Minecraft usernames, or Discord IDs without regard to capitalization or surrounding search spaces. Private browser session hashes and application answers are not searched. Empty filters select all records, and nonempty filters combine. Filtering runs over decrypted summaries before pagination, so matching records beyond the first page remain available. Returned counts and pagination cover only matches. The search and selections persist in list and detail URLs; applying or resetting a filter returns to the first page. Status changes do not expire or delete submitted records, including denied applications.

`/applications/editor` and `GET` or `PUT /api/application-forms` require Dashboard access and `applications.edit`, granted to Manager and Founder by default. Reads use the existing one-minute Discord role cache, invalidated by member updates. PUT forces a fresh role check, also requires the staff origin and session CSRF token, and is rate limited. Its body contains `version`, `role`, and `form`. A form contains a description, ordered question definitions, and scenario prompts. Question definitions have a stable key, title, help text, answer kind, required flag, minimum length, community condition, and choice options. New question keys use a UUID prefixed with `q_`; identity and flow keys cannot be introduced as custom questions. Limits are 40 questions and 40 scenarios per form, 160 characters per title, 1,500 per help text, 2,000 per scenario, and 12 distinct choice answers. The scenario response remains an unconditional required paragraph with at least 40 characters. The editor allows preview, reordering, removal with undo, and individual form saves.

Questionnaire catalogs are encrypted permanent `application-form-revision` records in the application database. `application-form-current` stores the published revision pointer. Baseline revision 6 preserves the built-in questionnaire. Each save updates one form while retaining the other three, creates an immutable revision, and changes the pointer in one transaction. A stale version returns `application_form_changed` with HTTP 409 without overwriting another editor's changes. The UI preserves unsaved edits on failure and offers an explicit reload of the latest version.

New drafts pin the published revision when created. Older drafts without a revision pin baseline 6. The public draft response supplies that revision's question definitions; applicants cannot patch their revision, questions, or assigned scenario. Conditional questions are selected from the applicant's chosen communities. Client and server share answer validation. Weekly hours remain a protected field in the details step even if the editable availability paragraph is removed. Public JSON bodies and form edits are limited to 1 MiB. Autosave sends the selected form’s question answers and protected fields, while the draft retains answers from other forms for role switching.

Submitted applications contain the pinned `questionnaireVersion`, active question definitions, answers, and assigned scenario. Staff review uses the stored definitions, so later wording changes and removals cannot change historical submissions. Legacy submissions without question snapshots use the built-in question labels. Starting another application creates a new draft using the current published version. Back up the application database and its encryption key together to preserve both submissions and questionnaire revisions.

## Shared staff email

`/email` and every `/api/mail` request require a valid staff session, a registered Minecraft name, the Dashboard access role and `mail.view`, granted to Admin, Manager and Founder by default. Huly access is not required. Mail uses the existing one-minute Discord role refresh; mutations force a fresh role check. Removing a rank invalidates access through the existing member-update path. SMTP sending requires `mail.send`, flag changes require `mail.flags`, and attachment downloads require `mail.attachments`. All mail mutations also require the exact staff Origin and session CSRF token. The public application and Huly hosts cannot access these routes. Mail responses have `Cache-Control: no-store`.

`mail.imapSocketPath` supplies a private IMAP socket. `mail.identities` allowlists up to twenty existing Proton sender addresses with display names. IMAP and SMTP reuse the Bridge credentials and certificate in `applications.smtp`, require STARTTLS and validate the certificate against loopback. The IMAP relay uses the supplied `proton-bridge-imap.socket` and service units, port 1143 and the existing private mail directory. Neither relay exposes a network listener. See [inbox setup](README.md#shared-email-inbox).

Folder selection must match an allowed selectable folder returned by IMAP. Standard mail folders, labels named for configured sender domains and optional `mail.folderPaths` are allowed. Other folder names are excluded from both listing and direct access. Lists search configured identities in To, Cc, Bcc, From and Delivered-To headers; selecting an address narrows that scope. An optional text search and unread filter combine before pagination. Pages fetch no more than twenty-five message summaries, newest UID first. The service bounds connections to four and does not mirror email contents into SQLite. Personal aliases not configured as identities are not selectable senders or mailbox filters. This is an address-scoped shared mailbox, not isolation between administrators.

Message reads, attachments, flag changes and reply threading validate the mailbox UIDVALIDITY and exact UID, then repeat the identity scope check. A changed UIDVALIDITY returns HTTP 409 instead of opening a potentially different message. MIME bodies are bounded to one MiB per text part. MailParser supplies decoded headers and HTML-only reply text; sanitize-html removes scripts, forms, styles, embedded objects, remote images and unsafe links. The UI uses escaped plain text or the sanitized HTML. Attachments are downloaded only on request, bounded to ten MiB, served as attachment downloads with an octet-stream content type, and never stored by the portal. Flag mutations are limited to Seen and Flagged; the reader does not delete or move mail.

The composer allowlists From addresses, validates up to twenty recipients across To, Cc and Bcc, rejects header injection, and limits the subject to 200 characters and the body to 50,000. Up to five file attachments may total ten MiB. Attachments are accepted as bounded base64 data and sent from memory; filesystem paths and remote URL attachments are unavailable. SMTP has file and URL access disabled. Reply Message-ID and References are derived from the authorized original message, never client-supplied headers. Proton stores its sent copy; the portal does not append another.

Interactive sending is limited to thirty requests per hour per Discord account. Each draft carries a stable random send ID. The encrypted staff database retains a payload hash, Message-ID and send result for thirty days, without a body or attachment copy. Concurrent duplicates are rejected; an accepted duplicate returns its original receipt. A changed payload with the same ID is rejected. An uncertain SMTP result is not retried automatically, including after restart. Staff must inspect Sent before starting a new draft. Partial recipient acceptance is shown explicitly. SMTP acceptance is not proof of inbox delivery. Draft content stays in React memory and is cleared when the composer closes or the page reloads. Navigation and discard warnings protect unsent drafts.

Unit and HTTP tests cover rank access, host and CSRF boundaries, scoped pagination, UIDVALIDITY changes, sanitizer behavior, MIME attachments, flag restrictions, header and sender validation, reply threading and duplicate or uncertain sends. Mail fixtures use in-memory databases and synthetic messages; the test suite sends no live email.

## Dashboard role management

`shared/staff-permissions.js` defines the dashboard capability catalog and required access dependencies. `server/role-permissions.js` merges stored per-role overrides with compatible defaults, combines grants across assigned Discord roles, and applies independent Dashboard and Todo admission gates. Permissions are recomputed on every protected request, including cached Discord sessions. Removing parent access also prevents dependent actions. Huly workspace synchronization records the policy revision; a saved policy change closes any now-unauthorized Huly sockets and triggers membership reconciliation at the next visit or sweep.

`GET /api/roles` returns the revision, ten configured role definitions, capability metadata, edit restrictions and Discord hierarchy information. Read routes reuse the existing one-minute Discord role cache, invalidated by member updates. Mutations perform one fresh role check before authorization rather than repeating an immediately completed lookup. `PUT /api/roles` saves the complete permission matrix with its expected revision. Only boolean values for known capabilities and configured role IDs are accepted. Revisions that changed since loading return 409. Mutations require the staff host, Origin and session CSRF token, and current Discord membership. Roles is restricted to actual Manager and Founder ranks in addition to its `roles.view`, `roles.edit` and `roles.assign` grants. Lower ranks cannot receive these management grants. Managers cannot alter the Founder matrix. Founder Dashboard and role-management grants cannot be turned off.

`GET /api/roles/members?name=...&offset=...` searches Discord names or a numeric user ID. Pages contain at most 25 members; name searches are bounded to 100 IDs across both guilds. An empty search uses the bot's cached roster. `POST /api/roles/members/{id}` accepts the member snapshot `version`, one community `rank` or null, specialist role IDs, and boolean Dashboard and Todo access choices. A changed snapshot returns 409. Only Founders may add or remove Manager and Founder, including their access roles. Self-removal of Founder or Dashboard access is rejected. Roles outside the configured managed set are preserved.

Community rank intent uses the existing bidirectional `discord-role-sync` worker. The worker checks the whole planned rank change against the bot hierarchy before removing an existing rank, so an inaccessible promotion retains the previous rank. Independent specialist and access-role intent uses encrypted `role-assignment` records with per-member serialization. Changes wait for missing members, screening or hierarchy and retry on member events, role changes and a bounded minute timer. Builder, Dev, Artist and access-role assignments are staff-server only unless matching roles are separately mapped. Minecraft integration remains absent; no Minecraft role change is attempted.

The staff database retains encrypted `role-permissions` revisions, `role-assignment` intents and `role-audit` entries without expiration. Audit history is available to authorized managers through `GET /api/roles/history`, in pages of 25. Back up these records with the existing staff database and its key. Policy editing does not change Discord's native permission bits or Huly's internal permission model. Applications continue to store author identities, final decisions and notification delivery independently.
